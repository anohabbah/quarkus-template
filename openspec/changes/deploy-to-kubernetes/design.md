# Design

## Context

See proposal.md for why. What exists today:

- **Packaging:** `./gradlew build` produces the fast-jar in `build/quarkus-app/`. The stock `src/main/docker/Dockerfile.*` files and `.dockerignore` assume that host-side build. Nothing uses them.
- **Health:** `/q/health/live` and `/q/health/ready` (database only) exist (`observability` spec). SmallRye Health also serves `/q/health/started`.
- **Runtime settings with no defaults:** `SALESFORCE_URL`, `SALESFORCE_CLIENT_ID`, `SALESFORCE_CLIENT_SECRET` and `quarkus.datasource.*` must be set, or the app fails at startup. `QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT` must be set for telemetry to leave the pod.
- **State:** none in the pod. Idempotency is enforced by Salesforce (`requestId`), and there are no JPA entities. Several replicas need no coordination. Flyway takes a PostgreSQL advisory lock, so pods that start together don't race on migrations.
- **Request duration:** a `POST /authorization-requests` can take up to about 22.5 s (3 attempts of at most 7 s, 250 to 750 ms apart).
- **Tests:** `@QuarkusTest` in `src/test`, and `XxxIT extends XxxTest` in `src/native-test` run by `testNative` against the packaged jar. Both use PostgreSQL Dev Services, so CI needs Docker (present on GitHub's Ubuntu runners).
- **Repo:** public on GitHub (`anohabbah/quarkus-template`), default branch `main`, no CI.

Facts checked in the Quarkus 3.40.1 test jars during planning:

- When the same build also builds a container image, Quarkus records the artifact as `jar-container`, and `@QuarkusIntegrationTest` then starts the image instead of the jar.
- The container launcher only offers `quarkus.test.container.network`, extra exposed ports, labels and volume mounts. It adds no host alias. `SalesforceStub` gives the app `http://localhost:<port>`, which doesn't reach the test JVM from inside a container. So the ITs must run in a build that doesn't produce an image (D5).

## Goals / Non-Goals

**Goals:**
- One command builds, and optionally pushes, the image and the manifests: `./gradlew build -Dquarkus.container-image.build=true`.
- Everything that is the same in every environment lives in the generated manifest. Overlays hold only what differs.
- No change to `src/main/java`, `src/test` or `src/native-test`.

**Non-Goals:**
- Running the ITs against the container image (decided during exploration: the staging rollout checks the image instead).
- Pinning by digest. The commit SHA tag is never re-pushed, so it is treated as immutable.
- Ingress, TLS, NetworkPolicies, PodDisruptionBudgets, HPA, and resource tuning beyond a starting point.
- Automating cluster-side setup (namespaces, RBAC, Secrets). It is documented, not scripted.

## Decisions

### D1. Jib through `quarkus-container-image-jib`

- Add `quarkus-kubernetes` and `quarkus-container-image-jib` with `addExtension`.
- In `application.properties`, set `quarkus.container-image.registry=ghcr.io` and `quarkus.container-image.group=anohabbah`. The name defaults to `quarkus.application.name` (`quarkus-template`). The tag defaults to the project version for local builds, and CI sets it to the commit SHA.
- Jib uses the Quarkus default JVM base image for Java 25 (a UBI OpenJDK runtime, the same family as the deleted `Dockerfile.jvm`). The exact image is recorded during apply.
- Pushing needs no Docker daemon. CI authenticates with `QUARKUS_CONTAINER_IMAGE_USERNAME=${{ github.actor }}` and `QUARKUS_CONTAINER_IMAGE_PASSWORD=${{ secrets.GITHUB_TOKEN }}` (`packages: write`).
- Delete `src/main/docker/` and `.dockerignore`, so there's only one image definition.

**Alternatives considered:**
- `quarkus-container-image-docker` with the existing `Dockerfile.jvm`. It works, but needs a daemon, builds less cacheable layers, and keeps two places where the image is defined.
- A multi-stage Dockerfile. That duplicates the Gradle build inside Docker, and Dev Services can't run tests inside a `docker build`.

### D2. Manifests generated by `quarkus-kubernetes`, as a build artifact

- The build writes `build/kubernetes/kubernetes.yml`: a Deployment, a Service (port 80 to 8080), and whatever else the extension generates by default (recorded during apply). The image reference in it carries the tag of that build.
- Settings in `application.properties`, same for every environment:
  - **Probes:** generated from SmallRye Health. Liveness on `/q/health/live`, readiness on `/q/health/ready`, startup on `/q/health/started`. The startup probe allows Flyway time at startup without a long liveness delay. If the extension doesn't generate the startup probe by itself, it's configured with `quarkus.kubernetes.startup-probe.*`.
  - **Environment:** `quarkus.kubernetes.env.configmaps=quarkus-template-config` and `quarkus.kubernetes.env.secrets=quarkus-template-secrets`, loaded whole (`envFrom`). The ConfigMap holds `SALESFORCE_URL`, `QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT` and `QUARKUS_DATASOURCE_JDBC_URL`. The Secret holds `SALESFORCE_CLIENT_ID`, `SALESFORCE_CLIENT_SECRET`, `QUARKUS_DATASOURCE_USERNAME` and `QUARKUS_DATASOURCE_PASSWORD`.
  - **Resources:** requests of `250m` CPU and `512Mi` memory, and a `512Mi` memory limit, with no CPU limit. The image's `run-java.sh` sizes the heap to 50% of the limit.
  - **No namespace** in the base. Each overlay sets it.
  - **Overrides of the extension's defaults** (found during apply, 3.1):
    - `quarkus.kubernetes.init-task-defaults.enabled=false`. By default the Flyway extension moves migrations into a `quarkus-template-flyway-init` Job, with a `k8s-wait-for` init container and a `view-jobs` Role and RoleBinding. A Job's pod template is immutable, so the next deploy with a new tag would fail at `kubectl apply`. Migrations stay at startup (`migrate-at-start`, advisory lock).
    - `quarkus.kubernetes.add-version-to-label-selectors=false`. Selectors are immutable, and the version label follows the project version, so a version bump would fail at `kubectl apply`.
    - `quarkus.kubernetes.startup-probe.failure-threshold=30`. The default allows about 35 s, which migrations at startup can exceed. 30 × 10 s gives about 5 minutes, with liveness unchanged.
- The manifest isn't committed. CI uploads `build/kubernetes/` from the job that built the image, and each deploy job applies that same artifact. Promotion therefore can't pick up a different image.

**Alternatives considered:**
- Committing the generated manifest (and checking it in CI for drift). Only needed for GitOps, which isn't used.
- Hand-written manifests or Helm. That means more files to keep in step with `application.properties`, while the extension already derives ports, probes and env.

### D3. Kustomize overlays per environment

```
deploy/
  base/kustomization.yaml          resources: [../../build/kubernetes/kubernetes.yml]
  overlays/staging/
    kustomization.yaml             resources: [../../base], namespace: staging, replicas: 1
    config.env                     -> configMapGenerator quarkus-template-config
  overlays/production/
    kustomization.yaml             resources: [../../base], namespace: production, replicas: 2
    config.env
  README.md                        cluster-side and GitHub setup
```

- Kustomize refuses files outside the kustomization root by default. The base reads `build/`, so it's rendered with `kubectl kustomize --load-restrictor LoadRestrictionsNone`.
- `configMapGenerator` adds a content hash to the ConfigMap name and rewrites the `envFrom` reference. A config change therefore rolls the pods.
- `config.env` files are committed with placeholder values (`https://example.my.salesforce.com`, and so on), because the real URLs belong to whoever runs the template. They must be replaced before the first deploy (task group 7).
- Resources are the same in both environments to begin with. A patch in `production` is the place to change them later.

### D4. Graceful shutdown

- `quarkus.shutdown.delay-enabled=true` with a `5s` delay, so readiness goes down and endpoints are removed before the server stops accepting requests.
- `quarkus.shutdown.timeout=25s`, so in-flight requests (up to about 22.5 s) can finish.
- `terminationGracePeriodSeconds: 40` on the Deployment, above the 30 s Quarkus can take. It goes in through `quarkus.kubernetes.*` if a key exists. Otherwise it goes in `src/main/kubernetes/kubernetes.yml`, which the extension merges into its output.
- If the delay doesn't make readiness report down in 3.40.1, the delay is dropped and recorded. Kubernetes then still stops routing during the timeout, with a brief window of refused connections.
- Checked during apply (4.3, Quarkus 3.40.1): after `SIGTERM`, `/q/health/ready` returns `503` at once (a `Graceful Shutdown` check reports DOWN), requests keep being served for the 5 s delay, and the server stops at 5.0 s. The delay is kept. `terminationGracePeriodSeconds` has no `quarkus.kubernetes.*` key, so it's set in `src/main/kubernetes/kubernetes.yml`.

### D5. GitHub Actions: one workflow, tests before the image

```
.github/workflows/ci.yml

on: pull_request, push to main

build  (all events)
  setup-java (Temurin 25), setup-gradle
  ./gradlew build testNative                      tests and ITs against the jar
  [main only]
  ./gradlew build -x test -x testNative \
     -Dquarkus.container-image.push=true \
     -Dquarkus.container-image.tag=$GITHUB_SHA    Jib push; regenerates build/kubernetes/
  upload artifact build/kubernetes/

deploy-staging     needs build, main only, environment: staging
deploy-production  needs deploy-staging, environment: production (required reviewers)
  download artifact -> build/kubernetes/
  write the KUBECONFIG environment secret to a file
  kubectl kustomize --load-restrictor LoadRestrictionsNone deploy/overlays/<env> | kubectl apply -f -
  kubectl rollout status deployment/quarkus-template -n <env> --timeout=5m
```

- The image is built in a second Gradle call **after** the tests. That way `testNative` runs against the jar (see Context). The second call skips the tests but still compiles, so NullAway still guards what's pushed.
- Each deploy job has a `concurrency` group per environment, without cancelling a deploy already running.
- Each GitHub Environment holds its own `KUBECONFIG` secret, for a ServiceAccount whose Role covers only that namespace. Staging jobs can't reach production.
- `kubectl rollout status` is what fails a deploy whose pods never become ready (spec "A failed staging rollout stops promotion", "A missing Secret stops the rollout").

**Alternatives considered:**
- Separate workflows for CI and deploy, chained by `workflow_run`. More moving parts for one service.
- `quarkus.kubernetes.deploy=true` from Gradle. It would need Gradle and cluster credentials in the same step, and it ignores the overlays.

### D6. Verification

This change has no production Java code, so it has no TDD slices (config, CI and docs are exempt). The spec scenarios are checked like this:

- **Generated output:** the rendered `kubectl kustomize` output for each overlay is inspected for the probes, `envFrom`, resources, grace period, namespace and replicas.
- **Local cluster (minikube is installed):** the image is built into minikube's registry, the staging overlay is applied with a hand-made Secret and a throwaway PostgreSQL, and the following are checked: readiness, traffic stopping when the database is down, the rollout failing when the Secret is missing, and a request in flight surviving `kubectl delete pod` against a slow stub.
- **Pipeline:** a pull request shows build and test only. The first push to `main` publishes `:<sha>`, deploys to staging, and waits for approval before production.

## Risks / Trade-offs

- [The base reads outside the kustomization root, which needs `LoadRestrictionsNone`] → The flag is passed only in the workflow and documented in `deploy/README.md`. The only file read from outside is the build's own output.
- [The image isn't covered by the ITs] → The image packages the same `quarkus-app/` the ITs ran against, and the staging rollout with its probes is the check.
- [Placeholder `config.env` values get deployed] → Readiness fails (no database) and `rollout status` fails the job before production. Group 7 replaces them before the first deploy.
- [GHCR packages start private] → The first deploy can't pull the image. `deploy/README.md` documents making the package public once (or adding a pull Secret).
- [The second Gradle call rebuilds instead of reusing outputs] → It only costs time. Recorded during apply.
- [`512Mi` is a guess] → Watch the JVM metrics in staging (already exported) and adjust per overlay.

## Migration Plan

1. Merge with the cluster-side setup done first (deploy/README.md): namespaces, ServiceAccounts and Roles, the `quarkus-template-secrets` Secret in each namespace, a reachable PostgreSQL, and the GitHub Environments with their `KUBECONFIG` secrets.
2. The first push to `main` publishes the image. Make the GHCR package public, then re-run the staging job if it failed to pull.
3. **Rollback:** re-run the deploy jobs of an earlier successful workflow run (its artifact names the earlier image), or `kubectl rollout undo deployment/quarkus-template -n <env>`. Flyway migrations aren't rolled back, so they must stay backward compatible.

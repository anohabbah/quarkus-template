# Proposal

## Why

The service can't be deployed anywhere today. `src/main/docker/` holds the stock Quarkus Dockerfiles, which need a host-side `./gradlew build` first and have never been used. Nothing builds or publishes an image, there are no Kubernetes manifests, and the repo (public on GitHub) has no CI at all. The target is a self-managed, vanilla Kubernetes cluster with a `staging` and a `production` namespace, deployed from a CI pipeline. This project is also a starter template, so every service built from it should inherit a working path from commit to cluster.

## What Changes

- **Container image built by Jib** (`quarkus-container-image-jib`), published to GHCR as `ghcr.io/anohabbah/quarkus-template`, tagged with the git commit SHA. One image per commit, promoted unchanged from staging to production.
- **Kubernetes manifests generated by `quarkus-kubernetes`**: a Deployment and a Service, with liveness, readiness and startup probes on the existing `/q/health/*` endpoints, resource requests and limits, and environment taken from a ConfigMap and a Secret referenced by name. The generated manifest is a build artifact and is never committed.
- **Per-environment Kustomize overlays** in `deploy/overlays/staging` and `deploy/overlays/production`, on top of the generated manifest: namespace, replicas, resources, and the non-secret settings (`SALESFORCE_URL`, OTLP endpoint, JDBC URL).
- **Graceful shutdown**: in-flight Salesforce calls (up to about 22.5 s with retries) finish before a pod stops during a rollout.
- **GitHub Actions pipeline**:
  - Pull requests build and run the JVM tests and the integration tests.
  - Pushes to `main` do the same, then push the image, deploy it to `staging`, and deploy the same image to `production` after a required review.
  - A deploy fails when the rollout doesn't become ready.
- **Removal:** `src/main/docker/*` (the JVM, legacy-jar, native and native-micro Dockerfiles) and `.dockerignore`. Jib replaces them. Anyone building images with those Dockerfiles must switch to `-Dquarkus.container-image.build=true`.
- **Docs:** the cluster-side setup the pipeline relies on (namespaces, a namespace-scoped deployer ServiceAccount per environment, the app Secrets, GHCR package visibility), and the `CLAUDE.md` commands and structure.

## Capabilities

### New Capabilities

- `deployment`: how the service is packaged, published and run on Kubernetes. Covers the image and its tagging, the probes and shutdown behaviour of the running pod, where configuration and secrets come from, and how a commit is promoted from staging to production.

### Modified Capabilities

None. The health endpoints in `observability` are reused as they are.

## Impact

- **API consumers:** no change.
- **Dependencies:** adds `quarkus-kubernetes` and `quarkus-container-image-jib` (versions from the BOM).
- **Code:** no change to `src/main/java`, `src/test` or `src/native-test`.
- **Configuration:** `application.properties` gains container-image, Kubernetes and shutdown settings. New `deploy/` directory with the Kustomize base and overlays, and `.github/workflows/`.
- **Operations:**
  - The cluster needs the `staging` and `production` namespaces, a deployer ServiceAccount with a Role limited to each namespace, and the app Secret (Salesforce client credentials, database credentials) in each.
  - GitHub needs `staging` and `production` Environments, each with a kubeconfig secret, and required reviewers on `production`.
  - The GHCR package must be made public once after the first push, or each namespace needs an image pull Secret.
  - PostgreSQL is provided outside this change.
- **Out of scope:** the database, Ingress and TLS, native images, autoscaling, and creating cluster-side objects.
- **Docs:** `CLAUDE.md` (commands, Dockerfile bullet, new deploy and CI notes), plus a `deploy/README.md` with the cluster and GitHub setup.
